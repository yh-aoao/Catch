# Roll link5 与底盘碰撞修复（2026-09-15）

用户日志为 `ranger_base` 对 `geom#60/body#15`，穿透约 0.6–1.5mm。
当前主 XML 按 body/geom 顺序核对：body15=link5，geom60=link5 碰撞 mesh。
这是机械臂自碰撞，不能通过放宽手桌距离、忽略底盘碰撞来解决。
运行时日志现在同时打印 body 名称，可核对服务器模型是否与本地一致。

## 修改

- 仅 Roll：IK 从实际六个臂关节角开始，避免内部未执行目标累积。
- 候选 IK 成功后，在独立 MjData 中按每关节最大约 0.03rad 的间隔检查关节插值路径。
  用 `mj_geomDistance` 检查 link2–link6、手掌和手指的有效碰撞 geom 到 ranger_base 的距离。
  默认余量 `roll_arm_base_margin=0.005m`。已经位于余量内时允许不进一步恶化的退让动作。
- 拒绝危险目标或 IK 失败时保持当前实测关节目标，并回滚辅助 IK 模型状态。
  使用已有约束罚分，实际碰撞仍终止；没有关掉碰撞或改变成功口径。
- Roll reset 的关节控制目标改为与实际 Roll 初始关节角一致，避免未来修改
  `roll_arm_joints` 后控制器又拉回通用初态。
- `[roll-check]` 增加 `guard_blocked`，碰撞日志增加实际 body 名称。

## 验证和局限

CPU 测试执行真实 guard 方法，覆盖危险目标拒绝、退让允许、实时状态不被试算改写。
已有奖励/策略回归一并运行。本机 MuJoCo DLL 无法加载，未完成真实网格距离及训练验证。
这不是动力学安全保证：检查 ranger_base 与臂、手的候选关节插值路径，
不能保证不同步关节运动、PID 超调、底盘倾斜或未检查部件的碰撞被拦截。
较旧 MuJoCo 的凸网格正距离查询也有精度限制，需以运行时接触日志验证。
API 参考：https://mujoco.readthedocs.io/en/3.2.6/APIreference/APIfunctions.html#mj-geomdistance

同步 `gym_dcmm/envs/DcmmVecEnv.py` 和 `configs/env/DcmmCfg.py` 到 Linux，先用原命令
设置 `num_envs=1 roll_log=true` 短跑。确认实际碰撞是否减少，以及是否频繁 guard_blocked。
如果一直被拒绝，应继续调整初始臂姿/可达拦截目标或检查控制器，不能直接取消检查。
旧策略可用于复测故障，新训练使用新输出目录，避免覆盖旧模型。

## 指尖碰撞补充修复

新日志明确碰撞双方为 base_link 和 fingertip，发生在约第 9 步、末端高度约 0.55m。
此前 guard 遗漏了手指，并且在生成手指目标前执行，因此不能阻止这类自碰撞。

- 将手掌及其手指子树的有效碰撞几何体加入检查。
- 在手指目标生成后、目标写入延迟队列前检查完整的 6 个臂关节和 16 个手关节。
- 拒绝危险目标时同时恢复臂、手实测姿态及辅助 IK 状态，继续沿用已有约束罚分。
- 保留真实碰撞终止；不通过忽略微小穿透或修改奖励权重掩盖问题。

增加固定机械臂时手指危险运动拒绝、手指退让允许及非有限目标拒绝的 CPU 回归测试。
本次同步 DcmmVecEnv.py 即可更新运行代码（依赖此前已有的 roll_rewards.py）。
仍需 Linux 真仿真复测：插值检查不能保证控制延迟、关节不同步或 PID 超调下无碰撞。
若仍第 9 步碰撞，应进一步检查初始手姿、延迟队列及实测关节轨迹，不能据此宣称已解决训练。

## 执行阶段检查（execution_guard_v1）

最新日志仍出现 fingertip_3、dip 与底盘接触，说明只检查新目标不足以保证实际执行安全。
当前 act_delay 的默认值均为 1，不能据此将故障定性为延迟队列问题。

Roll 现在在每个物理子步、PID 更新前，根据实测姿态重查将执行的臂手目标。
发现危险目标时清空臂手旧队列、将目标置为实测关节角、同步辅助 IK 状态，
并清理 PID 累积误差及微分历史，保留本回合随机化的增益。沿用已有约束罚分。
回合重置执行拦截计数。早期底盘碰撞新增 roll-control-check，输出版本标记、
执行拦截次数、臂手最大实测角速度及执行目标误差，便于区分检查遗漏与动力学偏差。

该修改增加几何查询次数，FPS 可能下降；仍不包含动力学预测或制动轨迹规划，
不能保证拦截后惯性、重力、噪声不会继续导致接触。不可通过瞬移实测关节消除碰撞。
需要 Linux 复测，尤其关注零动作轨迹也是否约第 9 步碰撞；如是，应优先检查初态和 PID。
奖励权重和成功/碰撞终止条件未修改。CPU 回归覆盖队列刷新、PID 历史清理及增益保留。
